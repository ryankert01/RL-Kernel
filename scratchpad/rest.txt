 突破 11　 坑 16
 版本三角 vLLM 0.31 要 transformers ≥5.10.4,<5.18，Megatron Bridge main 要 ≥5.15,<5.18（且 Python 3.12）：交集是 5.15–5.17，取其中最新的 5.17.0，指纹的语义源从 5.19 改钉 5.17。
 Bridge 的 PyPI 版没有这个模型 PyPI 上最新的 0.6.2 也还没有这个模型（且钉 transformers≤5.12.1；resolver 退到的 0.3.1 甚至钉 <5）；改为从 git main 可编辑安装。
 仓库的严格内核只认 Hopper FA4/SM90 内核和 _C 扩展在 A100 上不可用；原有 Triton det_gemm 只有 1–6 TFLOP/s（FFN 形状约 1–2），于是新树形 GEMM 成了必需行。
 约 10 个 agent 并行 每个 agent 一个 worktree、互不重叠的文件、GPU 租约；WS1 全部合并，316 个测试。
 agent worktree 从 main 拉出 不是从 POC 分支；每个 agent 先自己合并 POC 分支。
 LM head 被 GEMM 换代打破 fast_det_gemm 落地后 LM head 自动用它，K%256 契约让小形状测试挂掉；集成方加回退。（Wave A 发现这个回退本身违反“失败即关闭”。）
 52 层真权重逐 bit 相同 train = prefill = 4 种 chunk = decode，golden 和 Triton 两条后端都成立。
 TP/CP 在真实 NCCL 上成立 并用 NCCL all_reduce 的对照证明树是必要的。
 两波限流 会话限额和模型限额先后打断 agent；第二波打断了大部分 review agent，只保住了 35 条发现。
 vLLM 0.31 检查 __init__ 签名 *args/**kwargs 包装器把 vllm_config 藏起来了，严格 TP1 启动失败。
 两个 env 不能放进一个进程 编排器原设计是单进程同时 import 两个引擎；改为跨 env 的 trainer 桥（Wave A）。
 会话限额打断 Wave A 第二轮开工约一小时后到了用量上限：停掉 workflow，把每个 agent 的半成品存成提交，定时器 3 小时 10 分钟后自动恢复，只重启没做完的那一行。
 vLLM 严格 == 参考链：933/933 vLLM 0.31 的严格绑定在 30B 上对 9 条序列打分，和单卡参考链逐 bit 相同；TP2 == TP1，带随机 LoRA 也一样。
 vLLM 的 RPC 传不了嵌套张量 collective_rpc 用 msgpack，LoRA 的张量字典过不去；改成写节点本地文件、worker 读后重算哈希。
 rollout 自己和自己一致 严格 vLLM 在 TP1/TP2/TP4、贪心/采样、有无 LoRA 的 12 种组合里，decode 时记下的 logprob 与事后 prefill 重算 0/512 不同；原生是 144–168/512。
 训练侧 TP2 == TP1，连梯度都一样 Megatron 严格 trainer：logprob 0/933 不同，LoRA 梯度 832 个张量的聚合哈希一致，一步 AdamW 后 LoRA 哈希一致。
 TP1 训练 OOM Wave A：TP1 上单次 8192 token 的打包 OOM（权重就 56 GB），默认 micro batch 先改成 4096 token；wave B 把 RoPE 改为从规范缓存表取行（原来每种打包一份、无限增长），8192 token 在 TP1 上峰值 68.5 GiB 可以训练，4096 只剩内存旋钮的作用。
 两边的 LoRA 哈希不是同一个定义 Megatron 侧用 key+shape+bytes，E2E 用 name|dtype|shape；跨 env 桥的 agent 发现后统一到 muse_glimmer_lora_sha256_v1。
 Triton 把树折进了 MMA 链 K 很小时每个 K 块只迭代一次，编译器把树的 7 个加法折成 3 个，K=256/512 时 47–67% 的输出偏离契约；对抗 review 发现，强制两次迭代后修复。
 near-certain token 的 logp > 0 两遍 softcap 内核的第二遍被编译成 FMA，最大值的 exp 不是 1；关掉 FP 融合后 0/2048。
 torch 2.13 的 Adam 在 CPU 上也会碰 GPU CPU 参数的 optimizer.step 会建 CUDA context，占住 GPU 0；mock 改用 CPU 安全的 Adam。
 消融：原生漂移的来源 在 HF 上，拼 batch、KV cache decode、prefill 少一个 token、注意力实现、logits 精度、在 GPU 上算 RoPE 频率，任何一个都让 918–927/933 个 token 变 bit；TF32、换卡、换进程是 0。第一轮把“GPU 上算 inv_freq”误判为 0，review 发现那一项根本没在 GPU 上算。
 TP4 也逐 bit 相同 Megatron TP1 == TP2 == TP4：logprob、1.05 亿个 LoRA 梯度元素、AdamW 后的 LoRA 哈希全部一致；vLLM TP4 引擎 == TP1。
 梯度与打包方式无关 LoRA 权重梯度改为逐序列计算、按样本顺序左折叠，micro-batch 512/4096/8192 三种打包下梯度完全一样（以前在 3 条序列、一个列并行 LoRA 层的单元测试里，20,480 个梯度元素有 14,860 个随打包变化）。
 严格模式会悄悄降级 review 发现 Megatron 绑定在严格内核缺失时会退回 torch/cuBLAS；改成直接报错。vLLM 在退回 V1 model runner 时也会绕过严格路径，同样改成报错。
 rollout 在极端调度下仍然自洽 跨越 2048 窗口的长序列、chunked prefill、batch 256、KV 池小到发生 13 次抢占：严格 vLLM 的 decode 与 prefill 全部 0 差异。
 最终三方比对 参考链（两次运行）、vLLM TP1/2/4、Megatron TP1/2/4 共 8 份结果，加 3 份带 LoRA 的 vLLM 结果，全部来自 O7 修复之后；三个运行时调用同一套严格 Triton 内核，组内 0/933 不同。
 RFC 需要怎么改
 实现过程中才暴露的问题
 F1 · Numerical requirements / O5 (attention backward) O5 反向规则不是 CP 不变的 契约写的“dK/dV 按 query block 升序累加”在 CP 下做不到。已改为“整条序列 8 个规范 query 块、块间按 O3 树合并，每个 KV 头只在读它的 4 个 Q 头组之间合并”，单卡内核与 CP1/模拟 CP2/4/8/真实双卡 CP2 逐 bit 相同；代价是 T ≥ 1024 时反向慢 5–14%，T = 512 时慢 55–58%。 
 F2 · WS1 attention rows / WS2 TP 注意力内核要接受头数参数 已实现：注意力内核接受 H_Q/H_KV，TP2/4/8 每个 rank 只算自己的 16/1、8/1、4/1 个头，前向反向都是 TP1 的逐 bit 切片；复制的 KV 头的 dK/dV 由各副本 fp32 部分和按规范树合并。vLLM 与 Megatron 都已改用每 rank 自己的头数调用，不再把头 all-gather 回 32/2 的完整几何或补零调用；TP4/8 下 KV 头仍按契约在 t/2 个 rank 上复制（Megatron 用 GatherKVHead 按 rank 顺序收集 k/v 列分片）。 
 F3 · weight_sync_identity Bridge 把 final norm 存成 w−1 Megatron Bridge 把 model.language_model.norm.weight 存成 bf16 的 (w−1)，bf16(w_meg+1) 有 1120/6656 个元素和 HF 不同。weight_sync_identity 要写明：这个张量从 HF checkpoint 重载，预期 626/627 个张量逐字节相同。 
 F4 · Projection grouping (to-freeze) Bridge 的 fused linear_qkv 布局 每个 KV 组 g（4352 行）= [q 头 16g..16g+15（2048）| gate 头（2048）| k 头 g（128）| v 头 g（128）]；linear_fc1 = [gate; up]。已在真权重上 torch.equal 验证。严格路径要按这个布局拆开成四个独立 GEMM。 
 F5 · Validation table 梯度容差要和尺度无关 反向的比较用归一化误差（相对于参考梯度的范数），固定 atol 在 30B 的梯度尺度上没有意义。 
 F6 · Numerical requirements / O5 O5 要写明 m = −inf 保护 一行还没遇到可见的 key 时（局部窗口的边界、padding），m_new = −inf：这时减去 0 而不是 m_new（m_safe = 0）。于是 α = exp(−inf) = 0、p = 0，状态保持 (−inf, 0, 0)，不产生 NaN；遇到第一个可见 key 之后，这一步是逐 bit 的空操作。docs/contracts O5 已写入这条保护。 
 F7 · Open question 3 (LoRA) LoRA 不合并 两边都用 y = bf16(acc32(W·x) + Σ_k B[:,k]·z[k])，z = bf16(A·x)，对 rank 维按 k 升序做 fp32 顺序累加、只舍入一次；把 LoRA 合并进 W 会改变 bit。 
 F8 · WS1 table 几行要改名或合并 fused_add_rmsnorm → fused_post_norm_residual_pre_norm（四范数夹心，(1+w) 增益，两个 eps 1e-5 / 1e-8）；注意力的 train / rollout 两行合成一行、两种执行模式；vocab_parallel_softcap_logp 并入 WS1 的 lm_head 行 + 一个传输行。 
 F9 · Foundation / environment 版本钉在 transformers 5.17.0 vLLM 0.31 要 transformers ≥5.10.4,<5.18，Megatron Bridge main 要 ≥5.15,<5.18：交集是 5.15–5.17，取其中最新的 5.17.0（commit 856157a2），语义源从 5.19 改钉 5.17。5.17 用 K=1 的 fp32 matmul 构造 RoPE 角度，5.19 用 fp32 逐元素乘；在 A100 上两种构造、以及开关 TF32，logprob 都逐 bit 相同（消融 0/933）。严格路径在两个运行时都用自己固定的 fp32 CUDA 表，不依赖其中任何一种。 
 F10 · Hardware assumptions 不要假设 Hopper 仓库现有的严格内核（FA4 CuTe、SM90 线性 logp）在 A100 上不可用，原有 Triton 确定性 GEMM 只有 1–6 TFLOP/s（FFN 形状约 1–2）。RFC 应把“一个与架构无关的 Triton 参考实现”列为基础行，Hopper 专用内核作为优化行。 
 F11 · final_e2e_lora / runtime layout 两个运行时不能在一个进程里 vLLM 0.31（torch cu130）和 Megatron Bridge + TransformerEngine（torch cu129）装不进同一个环境；E2E 用跨进程 trainer 桥，只传 token id、trainer 的 fp32 logprob、fp32 的 dL/dlogp（代理 loss Σ lp·g 的梯度恰好是 g）和带哈希的 LoRA。Megatron 训练侧现已支持 TP4（TP8 未测，默认关闭）。 
 F12 · Numerical requirements / O7 两遍 tile 内核必须禁止 FP 融合 第二遍重算 zhat 时编译器把 softcap·tanh − m 融成一个 FMA，最大值的 exp 不再恰好是 1，near-certain token 的 logp 比 0 大 1–2 ulp（30B 上 48/1024 个生成 token）。契约要写明：重算同一个量的两遍必须产生同样的舍入（编译时关闭 FP contraction）。 
 F13 · O3 / dense_gemm_qualification 编译器可能把声明的树折掉 K 很小时每个 K 块只迭代一次，Triton 把 8 叶树的加法折进 MMA 累加链（7 个加法剩 3 个），K=256/512 的输出有 47–67% 偏离契约。“BLOCK_K 不改变 bit”的说法不成立。契约要求每块至少两次迭代，并检查编译后的 IR。 
 F14 · WS2 TP / backward 列并行 GEMM 的 dA 必须在舍入前合并 每个 rank 先把 dA 舍入到 bf16 再相加，TP2/4/8 时 37–41% 的元素和 TP1 不同。正确做法：每个 rank 输出 fp32 部分和，用规范树合并后只舍入一次。 
 F15 · O4 qknorm_scaled_rope RoPE 表必须在 CUDA 上用同一个函数构造 同一公式在 CPU 和 GPU 上构造，cos/sin 有 18–27%（平均约 23%）的表项 bit 不同；HF 在 CPU 上算 inv_freq，GPU 上算 64 个里有 4 个不同，会让 924/933 个 token 变 bit。契约 O4 已要求“一次构造、缓存同一个对象”，还应要求运行时记录表的哈希并在两边比较。 
 F16 · Training side / LoRA LoRA 梯度要与 micro-batch 打包无关 原实现的梯度依赖 micro-batch 怎么打包（单元测试：3 条序列、一个列并行 LoRA 线性层，1 个和 2 个 micro-batch 之间 20,480 个梯度元素里有 14,860 个不同）。现在 token 维的权重梯度逐序列计算、按样本顺序左折叠，512/4096/8192 三种打包结果一致。契约要写明这个规则。 
 F17 · Strict mode definition 严格模式必须“失败即关闭”，包括运行时选择 Megatron 绑定曾在严格内核缺失时静默回退；vLLM 在退回 V1 model runner 时严格路径被绕过。RFC 应列出严格模式下禁止的功能（V1 runner、prefix caching、KV offload、投机解码等）和必须报错的情形。 
 F18 · weight_sync_identity 哈希要在每个 worker 上对实际加载的张量重算 rollout 侧原来只回显编排器声明的哈希。现在每个 TP worker 对自己加载的 LoRA 重算 muse_glimmer_lora_sha256_v1，全部一致才算同步成功；torchrun 下的 trainer 每个 rank 也要比对。 
 F19 · Experiments / ablation 漂移指标要能区分大小，argmax 翻转要考虑并列 “bit 不同的 token 数”在原生栈上几乎总是 98–99%，要同时报告 |Δlogp|、全词表 KL 和按概率分桶；bf16 softcap logits 有精确并列，45 次 argmax 翻转里 39 次发生在并列处。 
 F20 · vLLM rollout token 选择必须读严格 logits 第一版绑定记录的是严格 logprob，但选 token 用的是原生 cuBLAS bf16 logits，近似并列时选中的 token 会随 batch 组成和 TP 变化。wave B 让 compute_logits 返回严格的 fp32 zhat，vLLM V2 的 seeded Gumbel 采样器 / argmax 从它选 token，不再跑原生 lm_head。RFC 应在严格模式下要求这一点，并把采样器自身的 kernel（温度除法、按 (seed, position) 生成的 Gumbel 噪声、argmax）声明为契约算子。

 The parenthetical is correct but now frozen and imprecise. The fingerprint pins four separate GEMMs (`OFFICIAL_PROJECTION_GROUPING.attention = [[q_proj],[k_proj],[v_proj],[gate_proj]]`, fail-closed on `qkv_proj`, `qkvg_proj`, `linear_qkv`) and also pins the MLP gate/up pair separate (fail-closed on `gate_up_proj`, `linear_fc1`), which the RFC sentence does not mention. Natively: Megatron Bridge `MuseGlimmerQKVGMapping` writes one `decoder.layers.*.self_attention.linear_qkv.weight` of 8,704 × 6,656 laid out per KV group as [16 Q heads | 16 gate heads | K | V] × 128 (MCore gated-attention layout; `merge_qkv_weights` with `attention_output_gate`); vLLM uses `QKVParallelLinear` `qkv_proj` (4,608 × 6,656) plus a separate `ColumnParallelLinear` `output_gate_proj` (HF `self_attn.gate_proj` renamed); SGLang does the same as vLLM. Both runtimes fuse MLP gate/up natively (vLLM `MergedColumnParallelLinear` `gate_up_proj`; Megatron `GatedMLPMapping` -> `linear_fc1`).
 and one grouping of the Q/K/V/gate projections. The fingerprint pins four separate GEMMs (`q_proj`, `k_proj`, `v_proj`, `gate_proj`, as stored in the checkpoint) and fails closed on `qkv_proj`, `qkvg_proj` and `linear_qkv`; natively, Megatron Bridge fuses all four into one `self_attention.linear_qkv` (8,704 × 6,656; per KV group `[16 Q | 16 gate | K | V]` heads of 128) while vLLM and SGLang fuse Q/K/V into `qkv_proj` (4,608 × 6,656) and keep the gate as a separate `output_gate_proj`.  The to-freeze list omits the gate's dtype, and the two native runtimes disagree on it. HF (semantics source) computes `attn_output * torch.sigmoid(self.gate_proj(hidden_states))` entirely in BF16 (gate_proj output BF16, sigmoid BF16, multiply BF16); vLLM and SGLang do the same in BF16. Megatron-LM's `_apply_output_gate` computes `x * torch.sigmoid(gate.float())` in FP32 and casts back to BF16, so a Megatron-native training side and an HF/vLLM rollout side differ in the gate path even with identical weights. The fingerprint's `OFFICIAL_FROZEN_SEMANTICS['output_gate']` has form/granularity/width/input/applied_to/bias but no compute-dtype field, so this is currently not frozen anywhere.
 The fingerprint also has to freeze what the configs do not state: the gate's width, where it is applied and its dtype (HF applies `sigmoid` and the multiply in BF16 on the BF16 `gate_proj` output; Megatron native computes `x * sigmoid(gate.float())` in FP32 and casts back, so the two native paths differ);

 The replication arithmetic is right but the 'no communication' claim only describes vLLM. `repeat_kv` is a repeat-interleave (expand on a new axis then reshape), so Q head h uses KV head floor(h/16): TP2 rank r holds exactly KV head r (no replication); TP4 rank r holds KV head floor(r/2) (2x replication); TP8 rank r holds floor(r/4) (4x). vLLM's `QKVParallelLinear` implements exactly this (`num_kv_head_replicas = tp/2`, `shard_rank = tp_rank // num_kv_head_replicas`) so the rollout forward needs no extra communication. Megatron-LM does NOT replicate when `num_query_groups` (2) < TP: it column-splits the fused QKV(G) projection across all TP ranks, all-gathers the activations across TP (`all_gather_last_dim_from_tensor_parallel_region`), then slices out the rank's KV group and Q/gate heads; the backward of that all-gather is a native reduce-scatter summing dK/dV over the group's 16 Q heads. Megatron Bridge's `MuseGlimmerSelfAttention` inherits this path unchanged. The backward sentence is also loose: at canonical TP8 each KV head is fed by exactly 4 canonical groups (ranks 0-3 -> KV 0, 4-7 -> KV 1), so the combine is a 4-leaf subtree of the 8-leaf tree, and it applies to dK, dV and the `k_proj`/`v_proj` weight gradients.
 - **2 KV heads.** `repeat_kv` is a repeat-interleave, so Q head *h* uses KV head ⌊h/16⌋ (heads 0–15 → KV 0, 16–31 → KV 1). TP2 needs no replication (rank *r* holds KV head *r*). At TP4 and TP8 each rank holds a copy of the KV head its Q heads use (rank *r* → KV head ⌊2r/TP⌋; 2× and 4× replication). This is what vLLM's `QKVParallelLinear` does natively, so the rollout forward needs no extra communication. Megatron native does **not** replicate: with `num_query_groups` (2) < TP it column-splits the fused QKV/gate projection, all-gathers the activations across TP and slices (`SelfAttention.get_query_key_value_tensors`), and the backward of that all-gather is a native reduce-scatter — so the replicated ownership map must be imposed on the training side by the VIME provider. For the backward pass, the proposal is to evaluate K/V gradients (dK, dV and the `k_proj`/`v_proj` weight gradients) per canonical Q-head group (4 heads) and combine them in the canonical tree at every physical TP, including TP1; each KV head sums exactly 4 groups, i.e. one 4-leaf subtree of the 8-leaf tree (canonical ranks 0–3 → KV 0, 4–7 → KV 1).

 澄清 D6 - **Vocabulary.** 202,048 is not a multiple of 128 × canonical TP, so it is padded to 202,752. The multiplier and soft cap are applied before the tile partials, and padded logits are excluded.
 Arithmetic verified (202,048 mod 1,024 = 320; 198 × 1,024 = 202,752; `padded_vocab_size()` in workload.py and the manifest agree). Worth stating: 202,048 is not even a multiple of 128 (= 1,578 × 128 + 64), each canonical shard is 25,344 = 198 tiles, and all 704 padded logits fall in canonical shard 7. Neither runtime pads natively — vLLM `pad_vocab_size(.., 64)` leaves 202,048 unchanged and Megatron Bridge sets `should_pad_vocab=False` with `make_vocab_size_divisible_by(202048) = 64` — so the 202,752 layout is imposed by the strict logprob path, which pads to the canonical vocab with −inf before the tile partials, exactly as the Qwen3 track does (151,936 → 152,576 at canonical_tp=8). The multiplier and tanh soft cap are elementwise, so 'before the tile partials' is well defined.
 - **Vocabulary.** 202,048 is not a multiple of 128 × canonical TP (202,048 = 197 × 1,024 + 320; it is not even a multiple of 128), so the canonical layout pads it to 202,752 = 198 × 1,024 (25,344 = 198 tiles of 128 per canonical shard; the 704 padded logits all fall in canonical shard 7).  澄清 D7 - **CP.** Local layers apply the window on absolute positions. The gate is applied after the `(out, lse)` merge.
 Both statements verified against the semantics source; they are terse enough that a reader cannot tell what rule is meant. `sliding_window_overlay` is `kv_idx > q_idx - sliding_window` AND causal on absolute (cache) positions, i.e. attend iff 0 <= q - k < 2048, so under the `allgather` contiguous-block layout a local-layer query block needs at most 2,047 keys from the preceding CP block. The gate is `sigmoid(gate_proj(x))` of the layer input (input_layernorm output), elementwise per query token, multiplied into the flattened attention output before `o_proj` — a per-query factor that must be applied once to the merged output.
 - **CP.** Local layers apply the window on absolute positions (attend iff 0 ≤ q_pos − k_pos < 2,048, i.e. `sliding_window_overlay` ∧ causal), so with the `allgather` layout a local-layer query block reads at most 2,047 keys from outside its own block (from the preceding CP block, or several when `seq_len / CP` < 2,047). The gate is a per-query elementwise factor `sigmoid(gate_proj(x))` of the layer input, multiplied into the merged attention output before `o_proj`; it is applied after the `(out, lse)` merge, never to the partials.
