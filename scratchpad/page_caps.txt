• 能做到：两个真实运行时，逐 bit 相同
• 同一个模型，为什么训练和推理算出来的 logprob 不一样
• 同样 8 个 fp32 数：从左到右加得到 0xbf808770，按 8 叶平衡树加得到 0xbf808400。浮点加法不满足结合律，顺序就是结果的一部分。
• RL 训练里，rollout 引擎（vLLM）生成 token 并记下每个 token 的 log p，训练引擎（Megatron）再对同样的 token 重算一次 log p，两者的比值进入 PPO/GRPO 的重要性权重。模型、权重、输入都一样，可两边的 GEMM 切块、注意力分块、TP 归约、算子融合各不相同，加法顺序不同，bit 就不同。这点差异在更新之前就会被当成“策略偏移”。
    RFC #501 的目标：给 Muse-Glimmer-30B 写一份数值契约，规定每一个归约的顺序、每一次舍入的位置，让 vLLM 和 Megatron 按同一份契约执行，逐 bit 相同，而不是“误差很小”。
• 这次 POC 做了什么

• RFC 里需要改的几个数
• 一棵树管住跨 rank 的加法
• 契约（docs/contracts/muse-glimmer-30b-strict-contract.md）给每个归约都定死顺序：GEMM 的 K 维、词表和 dK/dV 的 query 维切成 8 个固定的块，块内 fp32 累加，块间按一棵固定的平衡二叉树相加，再在声明的位置舍入一次（GEMM 输出舍入到 bf16；logits 保持 fp32）；注意力按 64 个 key 一块、升序做 online softmax；norm 是逐行固定顺序的归约。TP 只决定“谁算哪棵子树”，不改变树本身。

• 版本三角vLLM 0.31 要 transformers ≥5.10.4,<5.18，Megatron Bridge main 要 ≥5.15,<5.18（且 Python 3.12）：交集是 5.15–5.17，取其中最新的 5.17.0，指纹的语义源从 5.19 改钉 5.17。
• Bridge 的 PyPI 版没有这个模型PyPI 上最新的 0.6.2 也还没有这个模型（且钉 transformers≤5.12.1；resolver 退到的 0.3.1 甚至钉 <5）；改为从 git main 可编辑安装。
• 仓库的严格内核只认 HopperFA4/SM90 内核和 _C 扩展在 A100 上不可用；原有 Triton det_gemm 只有 1–6 TFLOP/s（FFN 形状约 1–2），于是新树形 GEMM 成了必需行。
• 约 10 个 agent 并行每个 agent 一个 worktree、互不重叠的文件、GPU 租约；WS1 全部合并，316 个测试。
• agent worktree 从 main 拉出不是从 POC 分支；每个 agent 先自己合并 POC 分支。
• LM head 被 GEMM 换代打破fast_det_gemm 落地后 LM head 自动用它，K%256 契约让小形状测试挂掉；集成方加回退。（Wave A 发现这个回退本身违反“失败即关闭”。）
• 52 层真权重逐 bit 相同train = prefill = 4 种 chunk = decode，golden 和 Triton 两条后端都成立。
• TP/CP 在真实 NCCL 上成立并用 NCCL all_reduce 的对照证明树是必要的。
• 两波限流会话限额和模型限额先后打断 agent；第二波打断了大部分 review agent，只保住了 35 条发现。
• vLLM 0.31 检查 __init__ 签名*args/**kwargs 包装器把 vllm_config 藏起来了，严格 TP1 启动失败。
• 两个 env 不能放进一个进程编排器原设计是单进程同时 import 两个引擎；改为跨 env 的 trainer 桥（Wave A）。
• 会话限额打断 Wave A第二轮开工约一小时后到了用量上限：停掉 workflow，把每个 agent 的半成品存成提交，定时器 3 小时 10 分钟后自动恢复，只重启没做完的那一行。
• vLLM 严格 == 参考链：933/933vLLM 0.31 的严格绑定在 30B 上对 9 条序列打分，和单卡参考链逐 bit 相同；TP2 == TP1，带随机 LoRA 也一样。
• vLLM 的 RPC 传不了嵌套张量collective_rpc 用 msgpack，LoRA 的张量字典过不去；改成写节点本地文件、worker 读后重算哈希。
• rollout 自己和自己一致严格 vLLM 在 TP1/TP2/TP4、贪心/采样、有无 LoRA 的 12 种组合里，decode 时记下的 logprob 与事后 prefill 重算 0/512 不同；原生是 144–168/512。
• 训练侧 TP2 == TP1，连梯度都一样Megatron 严格 trainer：logprob 0/933 不同，LoRA 梯度 832 个张量的聚合哈希一致，一步 AdamW 后 LoRA 哈希一致。
• TP1 训练 OOMWave A：TP1 上单次 8192 token 的打包 OOM（权重就 56 GB），默认 micro batch 先改成 4096 token；wave B 把 RoPE 改为从规范缓存表取行（原来每种打包一份、无限增长），8192 token 在 TP1 上峰值 68.5 GiB 可以训练，4096 只剩内存旋钮的作用。
• 两边的 LoRA 哈希不是同一个定义Megatron 侧用 key+shape+bytes，E2E 用 name|dtype|shape；跨 env 桥的 agent 发现后统一到 muse_glimmer_lora_sha256_v1。
• Triton 把树折进了 MMA 链K 很小时每个 K 块只迭代一次，编译器把树的 7 个加法折成 3 个，K=256/512 时 48–67% 的输出偏离契约；对抗 review 发现，强制两次迭代后修复。
• near-certain token 的 logp > 0两遍 softcap 内核的第二遍被编译成 FMA，最大值的 exp 不是 1；关掉 FP 融合后 0/2048。
• torch 2.13 的 Adam 在 CPU 上也会碰 GPUCPU 参数的 optimizer.step 会建 CUDA context，占住 GPU 0；mock 改用 CPU 安全的 Adam。
• 消融：原生漂移的来源在 HF 上，拼 batch、KV cache decode、prefill 少一个 token、注意力实现、logits 精度、在 GPU 上算 RoPE 频率，任何一个都让 918–927/933 个 token 变 bit；TF32、换卡、换进程是 0。第一轮把“GPU 上算 inv_freq”误判为 0，review 发现那一项根本没在 GPU 上算。
• TP4 也逐 bit 相同Megatron TP1 == TP2 == TP4：logprob、1.05 亿个 LoRA 梯度元素、AdamW 后的 LoRA 哈希全部一致；vLLM TP4 引擎 == TP1。
• 梯度与打包方式无关LoRA 权重梯度改为逐序列计算、按样本顺序左折叠，micro-batch 512/4096/8192 三种打包下梯度完全一样（以前在 3 条序列、一个列并行 LoRA 层的单元测试里，20,480 个梯度元素有 14,860 个随打包变化）。
• 严格模式会悄悄降级review 发现 Megatron 绑定在严格内核缺失时会退回 torch/cuBLAS；改成直接报错。vLLM 在退回 V1 model runner 时也会绕过严格路径，同样改成报错。
• rollout 在极端调度下仍然自洽跨越 2048 窗口的长序列、chunked prefill、batch 256、KV 池小到发生 13 次抢占：严格 vLLM 的 decode 与 prefill 全部 0 差异。
• 最终三方比对参考链（两次运行）、vLLM TP1/2/4、Megatron TP1/2/4 共 8 份结果，加 3 份带 LoRA 的 vLLM 结果，全部来自 O7 修复之后；三个运行时调用同一套严格 Triton 内核，组内 0/933 不同。
