在一台 8×A100 上，用真实的 vLLM 0.31 做 rollout、真实的 Megatron Bridge 做 LoRA 训练，按一份数值契约把每一次加法的顺序钉死，再跑 GRPO 看两边的 logprob 是否逐 bit 相同。这篇是结果、过程，以及 RFC 需要怎么改。

RL 训练里，rollout 引擎（vLLM）生成 token 并记下每个 token 的 log p，训练引擎（Megatron）再对同样的 token 重算一次 log p，两者的比值进入 PPO/GRPO 的重要性权重。模型、权重、输入都一样，可两边的 GEMM 切块、注意力分块、TP 归约、算子融合各不相同，加法顺序不同，bit 就不同。这点差异在更新之前就会被当成“策略偏移”。

两两比较：fp32 logprob 的 bit 不同的 token 数（共 933 个 token）
同一份 token（8 道 GSM8K 题 + 答案，1 条 2439 token、跨越 2048 窗口的长序列），每个实现输出每个 token 的 fp32 logprob。绿色 0 = 逐 bit 相同。无 LoRA：8 份 dump 两两 0 差异；同一个随机 LoRA：vLLM TP1/TP2/TP4 共 3 份 dump 两两 0 差异（Megatron 侧的 LoRA 对比见下面的 GRPO 端到端结果）。vLLM、Megatron 的原生实现（同一权重、无 LoRA）两两之间有 921–927 个 token 不同，加上 HF bf16 是 921–930 个。golden 是另一套固定顺序的严格实现（PyTorch fp32 算子 + Triton fp32 GEMM，bf16 只在契约规定的位置舍入，自身 prefill/decode/分块逐 bit 一致），算子分解和 Triton 后端不同，所以和严格路径有 894 个 token 不同；它是精度对照，不是逐 bit 目标。

原生 HF 栈的漂移从哪来：GEMM/注意力的形状与调度、RoPE 表在哪构造、logits 精度，任何一处变化
在 HF 模型上一次只改一个因素，对同样 9 条序列打分，和基线逐 bit 比较。重复跑、换一张卡、换一个进程、打开 TF32、RoPE 改成逐元素构造都是 0。但只要 bf16 GEMM 或注意力的形状、调度变了（拼 batch 加 padding、KV cache 逐 token decode、prefill 少一个 token、SDPA 换 eager、cuBLAS 的降精度归约开关），933 个 token 里就有 918–927 个变 bit；在 GPU 上而不是 CPU 上算 RoPE 的 inv_freq，64 个频率里有 4 个不同，也会让 924 个 token 变 bit。分块 prefill 只影响比块更长的序列：对比一次性 prefill，块 1024 只改了那条 2439 token 的长序列（176/933），块 64 改了 925/933。vLLM 这样的 rollout 引擎会同时改变其中好几个因素（批处理、KV cache decode、分块 prefill）；这一点是推断，本节只跑了 HF 和严格参考，没有跑 vLLM/Megatron。

vLLM 0.31 要 transformers ≥5.10.4,<5.18，Megatron Bridge main 要 ≥5.15,<5.18（且 Python 3.12）：交集是 5.15–5.17，取其中最新的 5.17.0，指纹的语义源从 5.19 改钉 5.17。
Bridge 的 PyPI 版没有这个模型
PyPI 上最新的 0.6.2 也还没有这个模型（且钉 transformers≤5.12.1；resolver 退到的 0.3.1 甚至钉 <5）；改为从 git main 可编辑安装。
仓库的严格内核只认 Hopper
FA4/SM90 内核和 _C 扩展在 A100 上不可用；原有 Triton det_gemm 只有 1–6 TFLOP/s（FFN 形状约 1–2），于是新树形 GEMM 成了必需行。
约 10 个 agent 并行
每个 agent 一个 worktree、互不重叠的文件、GPU 租约；WS1 全部合并，316 个测试。
agent worktree 从 main 拉出
不是从 POC 分支；每个 agent 先自己合并 POC 分支。
LM head 被 GEMM 换代打破
fast_det_gemm 落地后 LM head 自动用它，K%256 契约让小形状测试挂掉；集成方加回退。（Wave A 发现这个回退本身违反“失败即关闭”。）
52 层真权重逐 bit 相同
train = prefill = 4 种 chunk = decode，golden 和 Triton 两条后端都成立。
TP/CP 在真实 NCCL 上成立
并用 NCCL all_reduce 的对照证明树是必要的。
两波限流
会话限额和模型限额先后打断 agent；第二波打断了大部分 review agent，只保住了 35 条发现。
vLLM 0.31 检查 __init__ 签名
*args/**kwargs 包装器把 vllm_config 藏起来了，严格 TP1 启动失败。
两个 env 不能放进一个进程
编排器原设计是单进程同时 import 两个引擎；改为跨 env 的 trainer 桥（Wave A）。
会话限额打断 Wave A
第二轮开工约一小时后到了用量上限：停掉 workflow，把每个 agent 的半成品存成提交，定时器 3 小时 10 分钟后自动恢复，只重启没做完的那一行。
vLLM 严格 == 参考链：933/933
vLLM 0.31 的严格绑定在 30B 上对 9 条序列打分，和单卡参考链逐 bit 相同；TP2 == TP1，带随机 LoRA 也一样。
vLLM 的 RPC 传不了嵌套张量
collective_rpc 用 msgpack，LoRA 的张量字典过不去；改成写节点本地文件、worker 读后重算哈希。
rollout 自己和自己一致
严格 vLLM 在 TP1/TP2/TP4、贪心/采样、有无 LoRA 的 12 种组合里，decode 时记下的 logprob 与事后 prefill 重算 0/512 不同；原生是 144–168/512。
训练侧 TP2 == TP1，连梯度都一样
Megatron 严格 trainer：logprob 0/933 不同，LoRA 梯度 832 个张量的聚合哈希一致，一步 AdamW 后 LoRA 哈希一致。
TP1 训练 OOM
Wave A：TP1 上单次 8192 token 的打包 OOM（权重就 56 GB），默认 micro batch 先改成 4096 token；wave B 把 RoPE 改为从规范缓存表取行（原来每种打包一份、无限增长），8192 token 在 TP1 上峰值 68.5 GiB 可以训练，4096 只剩内存旋钮的作用。
两边的 LoRA 哈希不是同一个定义
Megatron 侧用 key+shape+bytes，E2E 用 name|dtype|shape；跨 env 桥的 agent 发现后统一到 muse_glimmer_lora_sha256_v1。
Triton 把树折进了 MMA 链
K 很小时每个 K 块只迭代一次，编译器把树的 7 个加法折成 3 个，K=256/512 时 48–67% 的输出偏离契约；对抗 review 发现，强制两次迭代后修复。
near-certain token 的 logp > 0
两遍 softcap 内核的第二遍被编译成 FMA，最大值的 exp 不是 1；关掉 FP 融合后 0/2048。
torch 2.13 的 Adam 在 CPU 上也会碰 GPU
CPU 参数的 optimizer.step 会建 CUDA context，占住 GPU 0；mock 改用 CPU 安全的 Adam。
消融：原生漂移的来源
在 HF 上，拼 batch、KV cache decode、prefill 少一个 token、注意力实现、logits 精度、在 GPU 上算 RoPE 频率，任何一个都让 918–927/933 个 token 变 bit；TF32、换卡、换进程是 0。第一轮把“GPU 上算 inv_freq”误判为 0，review 发现那一项根本没在 GPU 上算。
TP4 也逐 bit 相同
Megatron TP1 == TP2 == TP4：logprob、1.05 亿个 LoRA 梯度元素、AdamW 后的 LoRA 哈希全部一致；vLLM TP4 引擎 == TP1。
梯度与打包方式无关
LoRA 权重梯度改为逐序列计算、按样本顺序左折叠，micro-batch 512/4096/8192 三种打包下梯度完全一样（以前在 3 条序列、一个列并行 LoRA 层的单元测试里，20,480 个梯度元素有 14,860 个随打包变化）。
严格模式会悄悄降级
review 发现 Megatron 绑定在严格内核缺失时会退回 torch/cuBLAS；改成直接报错。vLLM 在退回 V1 model runner 时也会绕过严格路径，同样改成报错。
rollout 在极端调度下仍然自洽
跨越 2048 窗口的长序列、chunked prefill、batch 256、KV 池小到发生 13 次抢占：严格 vLLM 的 decode 与 prefill 全部 0 差异。
最终三方比对
参考链（两次运行）、vLLM TP1/2/4、Megatron TP1/2/4 共 8 份结果，加 3 份带 LoRA 的 vLLM 结果，全部来自 O7 修复之后；三个运行时调用同一套严格 Triton 内核，组内 0/933 不同。
结论
RFC 需要怎么改
实现过程中才暴露的问题
F1 · Numerical requirements / O5 (attention backward)
O5 反向规则不是 CP 不变的
契约写的“dK/dV 按 query block 升序累加”在 CP 下做不到。已改为“整条序列 8 个规范 query 块、块间按 O3 树合并，每个 KV 头只在读它的 4 个 Q 头组之间合并”，单卡内核与 CP1/模拟 CP2/4/8/真实双卡 CP2 逐 bit 相同；代价是 T ≥ 1024 时反向慢 5–14%，T = 512 时慢 55–58%。
F2 · WS1 attention rows / WS2 TP
注意力内核要接受头数参数
已实现：注意力内核接受 H_Q/H_KV，TP2/4/8 每个 rank 只算自己的 16/1、8/1、4/1 个头，前向反向都是 TP1 的逐 bit 切片；复制的 KV 头的 dK/dV 由各副本 fp32 部分和按规范树合并。vLLM 与 Megatron 都已改用每 rank 自己的头数调用，不再把头 all-gather 回 32/2 的完整几何或补零调用；TP4/8 下 KV 头仍按契约在 t/2 个 rank 上复制（Megatron 用 GatherKVHead 按 rank 顺序收集 k/v 列分片）。
F3 · weight_sync_identity
Bridge 把 final norm 存成 w−1
Megatron Bridge 把 model.language_model.norm.weight 存成 bf16 的 (w−1)，bf16(w_meg+1) 有 1120/6656 个元素和 HF 不同。weight_sync_identity 要写明：这个张量从 HF checkpoint 重载，预期 626/627 个张量逐字节相同。
F4 · Projection grouping (to-freeze)
Bridge 的 fused linear_qkv 布局
每个 KV 组 g（4352 行）= [q 头 16g..16g+15（2048）| gate 头（2048）| k 头 g（128）| v 头 g（128）]；linear_fc1 = [gate; up]。已在真权重上 torch.equal 验证。严格路径要按这个布局拆开成四个独立 GEMM。
F5 · Validation table
梯度容差要和尺度无关
反向的比较用归一化误差（相对于参考梯度的范数），固定 atol 在 30B 的梯度尺度上没有意义。
F6 · Numerical requirements / O5
O5 要写明 m = −inf 保护
一行还没遇到可见的 key 时（局部窗口的边界、padding），m_new = −inf：这时减去 0 而不是 m_new（m_safe = 0）。于是 α = exp(−inf) = 0、p = 0，状态保持 (−inf, 0, 0)，不产生 NaN；遇到第一个可见 key 之后，这一步是逐 bit 的空操作。docs/contracts O5 已写入这条保护。
F7 · Open question 3 (LoRA)
LoRA 不合并
两边都用 y = bf16(acc32(W·x) + Σ_k B[:,k]·z[k])，z = bf16(A·x)，对 rank 维按 k 升序做 fp32 顺序累加、只舍入一次；把 LoRA 合并进 W 会改变 bit。
F8 · WS1 table
几行要改名或合并
fused_add_rmsnorm → fused_post_norm_residual_pre_norm（四范数夹心，(1+w) 增益，两个 eps 1e-5 / 1e-8）；注意力的 train / rollout 两行合成一行、两种执行模式；vocab_parallel_softcap_logp 并入 WS1 的 lm_head 行 + 一个传输行。
F9 · Foundation / environment
版本钉在 transformers 5.17.0
vLLM 0.31 要 transformers ≥5.10.4,<5.18，Megatron Bridge main 要 ≥5.15,<5.18：交集是 5.15–5.17，取其中最新的 5.17.0（commit 856157a2），语义源从 5.19 改钉 5.17。5.17 用 K=1 的 fp32 matmul 构造 RoPE 角度，5.19 用 fp32 逐元素乘；在 A100 上两种构造、以及开关 TF32，logprob 都逐 bit 相同（消融 0/933）。严格路径在两个运行时都用自己固定的 fp32 CUDA 表，不依赖其中任何一种。
F10 · Hardware assumptions
不要假设 Hopper
仓库现有的严格内核（FA4 CuTe、SM90 线性 logp）在 A100 上不可用，原有 Triton 确定性 GEMM 只有 1–6 TFLOP/s（FFN 形状约 1–2）。RFC 应把“一个与架构无关的 Triton 参考实现”列为基础行，Hopper 专用内核作为优化行。
F11 · final_e2e_lora / runtime layout
两个运行时不能在一个进程里
vLLM 0.31（torch cu130）和 Megatron Bridge + TransformerEngine（torch cu129）装不进同一个环境；E2E 用跨进程 trainer 桥，只传 token id、trainer 的 fp32 logprob、fp32 的 dL/dlogp（代理 loss Σ lp·g 的梯度恰好是 g）和带哈希的 LoRA。Megatron 训练侧现已支持 TP4（TP8 未测，默认关闭）。
F12 · Numerical requirements / O7
两遍 tile 内核必须禁止 FP 融合
第二遍重算 zhat 时编译器把 softcap·tanh − m 融成一个 FMA，最大值的 exp 不再恰好是 1，near-certain token 的 logp 比 0 大 1–2 ulp（30B 上 48/1024 个生成 token）。契约要写明：重算同一个量的两遍必须产生同样的舍入（编译时关闭 FP contraction）。
F13 · O3 / dense_gemm_qualification
编译器可能把声明的树折掉
K 很小时每个 K 块只迭代一次，Triton 把 8 叶树的加法折进 MMA 累加链（7 个加法剩 3 个），K=256/512 的输出有 48–67% 偏离契约。“BLOCK_K 不改变 bit”的说法不成立。契约要求每块至少两次迭代，并检查编译后的 IR。
F14 · WS2 TP / backward
列并行 GEMM 的 dA 必须在舍入前合并
每个 rank 先把 dA 舍入到 bf16 再相加，TP2/4/8 时 37–41% 的元素和 TP1 不同。正确做法：每个 rank 输出 fp32 部分和，用规范树合并后只舍入一次。
F15 · O4 qknorm_scaled_rope
RoPE 表必须在 CUDA 上用同一个函数构造
同一公式在 CPU 和 GPU 上构造，cos/sin 有 18–27%（平均约 23%）的表项 bit 不同；HF 在 CPU 上算 inv_freq，GPU 上算 64 个里有 4 个不同，会让 924/933 个 token 变 bit。契约 O4 已要求“一次构造、缓存同一个对象”，还应要求运行时记录表的哈希并在两边比较。
F16 · Training side / LoRA
LoRA 梯度要与 micro-batch 打包无关
原实现的梯度依赖 micro-batch 怎么打包（单元测试：3 条序列、一个列并行 LoRA 线性层，1 个和 2 个 micro-batch 之间 20,480 个梯度元素里有 14,860 个不同）。现在 token 维的权重梯度逐序列计算、按样本顺序左折叠，512/4096/8192 三种打包结果一致。契约要写明这个规则。
F17 · Strict mode definition
严格模式必须“失败即关闭”，包括运行时选择
Megatron 绑定曾在严格内核缺失时静默回退；vLLM 在退回 V1 model runner 时严格路径被绕过。RFC 应列出严格模式下禁止的功能（V1 runner、prefix caching、KV offload、投机解码等）和必须报错的情形。
F18 · weight_sync_identity
哈希要在每个 worker 上对实际加载的张量重算
rollout 侧原来只回显编排器声明的哈希。现在每个 TP worker 对自己加载的 LoRA 重算 muse_glimmer_lora_sha256_v1，全部一致才算同步成功；torchrun 下的 trainer 每个 rank 也要比对。
F19 · Experiments / ablation
漂移指标要能区分大小，argmax 翻转要考虑并列
“bit 不同的 token 数”在原生栈上几乎总是 98–99%，要同时报告 |Δlogp|、全词表 KL 和按概率分桶；bf16 softcap logits 有精确并列，45 次 argmax 翻转里 39 次发生在并列处。
F20 · vLLM rollout
token 选择必须读严格 logits
第一版绑定记录的是严格 logprob，但选 token 用的是原生 cuBLAS bf16 logits，近似并列时选中的 token 会随 batch 组成和 TP 变化。wave B 让 compute_logits 返回严格的 fp32 zhat，vLLM V2 的 seeded Gumbel 采样器 / argmax 从它选 token，不再跑原生 lm_head。RFC 应在严格模式下要求这一点，并把采样器自身的 kernel（温度除法、按 (seed, position) 生成的 Gumbel 噪声、argmax）声明为契约算子。

The fingerprint freezes what the config does not state (read from `modeling_muse_glimmer.py` at the transformers commit pinned in `museglimmer_manifest.json` `semantics_source`; the 5.17.0 and 5.19.0 files are identical for every item below):

- **Output gate:** `self_attn.gate_proj` 6656→4096, no bias, input = `input_layernorm` output; `attn_out ⊙ sigmoid(gate)` elementwise over the flattened 32×128 attention output, before `o_proj`.
- **Q/K norm:** weightless RMSNorm per head over the 128 channels, fp32 compute (`x · (mean(x²) + eps)^-0.5`), `eps = rms_norm_eps`, cast back to BF16; then Q × `qk_scale_factor` (3.87) in BF16, K unscaled; order proj → norm → Q-scale → RoPE → KV-cache write. Softmax scale stays `head_dim**-0.5`.
- **`post_norm_eps`** governs `post_attention_layernorm` and `post_feedforward_layernorm` only; every other norm uses `rms_norm_eps`. Layer norms are Gemma-style `(1 + w)` RMSNorm in fp32 with `rsqrt`; the final norm is plain `w` RMSNorm.
- **Embedding norm:** lookup in BF16 → weightless RMSNorm, fp32, `eps = rms_norm_eps`, no √hidden scale → BF16.
- **Logits:** `20 · tanh((z · 0.19611613513818404) / 20)` — multiplier first, then the cap, in the model dtype (BF16).
- **RoPE:** all 128 head channels rotated, `rotate_half` layout, `rope_type: default`, cos/sin computed in fp32 and cast to BF16; applied only where `layer_rope_theta[i] != 0` (the `sliding_attention` layers); the per-layer value is a NoPE switch only — `inv_freq` always comes from `rope_parameters.rope_theta`.
- **Local window:** attend iff `0 ≤ q_pos − k_pos < 2048` on absolute positions (self + 2,047 past keys); the HF cache keeps the last 2,047 K/V rows after every update (`DynamicSlidingWindowLayer`).

- **2 KV heads.** `repeat_kv` is a repeat-interleave, so Q head *h* uses KV head ⌊h/16⌋ (heads 0–15 → KV 0, 16–31 → KV 1). TP2 needs no replication (rank *r* holds KV head *r*). Megatron native does **not** replicate: with `num_query_groups` (2) < TP it column-splits the fused QKV/gate projection, all-gathers the activations across TP and slices (`SelfAttention.get_query_key_value_tensors`), and the backward of that all-gather is a native reduce-scatter — so the replicated ownership map must be imposed on the training side by the VIME provider.
