问题

同一个模型，为什么训练和推理算出来的 logprob 不一样

RL 训练里，rollout 引擎（vLLM）生成 token 并记下每个 token 的 log p，训练引擎（Megatron）再对同样的 token 重算一次 log p，两者的比值进入 PPO/GRPO 的重要性权重。模型、权重、输入都一样，可两边的 GEMM 切块、注意力分块、TP 归约、算子融合各不相同，加法顺序不同，bit 就不同。这点差异在更新之前就会被当成“策略偏移”。

RFC #501 的目标：给 Muse-Glimmer-30B 写一份数值契约，规定每一个归约的顺序、每一次舍入的位置，让 vLLM 和 Megatron 按同一份契约执行，逐 bit 相同，而不是“误差很小”。

数值契约

一棵树管住所有加法

契约（docs/contracts/muse-glimmer-30b-strict-contract.md）把每个长归约都切成 8 个固定的块，块内 fp32 累加，块间按一棵固定的平衡二叉树相加，最后只舍入一次到 bf16。TP 只决定“谁算哪棵子树”，不改变树本身。

WS1 · 单卡算子

每个算子都有一个“逐 bit 确定”的版本，速度够用

仓库原有的严格内核（FA4 CuTe 注意力、线性 logp）只支持 Hopper，编译扩展 rl_engine._C 也无法对 CUDA 13 的 torch 构建，所以这次全部算子都是 PyTorch golden + Triton 重写。判断标准：同一个输入，不论 batch 怎么拼、序列怎么切、在第几个位置，输出 bit 都一样；和 fp64 参考的误差在 ws1 容差内。

WS2 · 多卡

TP 和 CP：切卡不改变加法顺序

修正的契约缺陷：契约 O5 原来的反向规则“dK/dV 按 query block 升序累加”不是 CP 不变的（每个 rank 只有自己的 query 块）。现在 O5 改成“整条序列 8 个规范 query 块，块间按 O3 树合并；每个 KV 头只在读它的 4 个 Q 头组之间合并”，单卡内核和 CP 路径共用同一条规则。

消融

原生栈的漂移从哪来：几乎任何一个执行细节

在 HF 模型上一次只改一个因素，对同样 9 条序列打分，和基线逐 bit 比较。TF32、RoPE 表怎么构造、换一张卡、换一个进程都不影响结果（null 对照全是 0）；但 batch 怎么拼、有没有 KV cache、prefill 怎么切、注意力用哪个实现、logits 用什么精度，任何一个都会让 98–99% 的 token 变 bit。rollout 引擎恰好同时改了这几个因素。

过程

一路上的坑和突破

突破 7　坑 15

  1. 版本三角

    vLLM 0.31 要 transformers<5.18，Megatron Bridge main 要 ≥5.15,<5.18 且 Python 3.12：只有 5.17.0 两边都接受，指纹的语义源从 5.19 改钉 5.17。

  2. Bridge 的 PyPI 版没有这个模型

    PyPI 0.3.1 还钉着 transformers<5；改为从 git main 可编辑安装。

  3. 仓库的严格内核只认 Hopper

    FA4/SM90 内核和 _C 扩展在 A100 上不可用；原有 Triton det_gemm 只有 5 TFLOP/s，于是新树形 GEMM 成了必需行。

  4. 13 个 agent 并行

    每个 agent 一个 worktree、互不重叠的文件、GPU 租约；WS1 全部合并，316 个测试。

  5. agent worktree 从 main 拉出

    不是从 POC 分支；每个 agent 先自己合并 POC 分支。

  6. LM head 被 GEMM 换代打破

    fast_det_gemm 落地后 LM head 自动用它，K%256 契约让小形状测试挂掉；集成方加回退。（Wave A 发现这个回退本身违反“失败即关闭”。）

  7. 52 层真权重逐 bit 相同

    train = prefill = 4 种 chunk = decode，golden 和 Triton 两条后端都成立。

  8. TP/CP 在真实 NCCL 上成立

    并用 NCCL all_reduce 的对照证明树是必要的。

  9. 两波限流

    会话限额和模型限额先后打断 agent；第二波让 43 个 review agent 死了 36 个。

  10. vLLM 0.31 检查 __init__ 签名

    *args/**kwargs 包装器把 vllm_config 藏起来了，严格 TP1 启动失败。

  11. 两个 env 不能放进一个进程

    编排器原设计是单进程同时 import 两个引擎；改为跨 env 的 trainer 桥（Wave A）。

  12. 会话限额打断 Wave A

    第二轮开工约一小时后到了用量上限：停掉 workflow，把每个 agent 的半成品存成提交，定时器 3 小时 10 分钟后自动恢复，只重启没做完的那一行。

  13. vLLM 严格 == 参考链：933/933

    vLLM 0.31 的严格绑定在 30B 上对 9 条序列打分，和单卡参考链逐 bit 相同；TP2 == TP1，带随机 LoRA 也一样。

  14. vLLM 的 RPC 传不了嵌套张量

    collective_rpc 用 msgpack，LoRA 的张量字典过不去；改成写节点本地文件、worker 读后重算哈希。

  15. rollout 自己和自己一致

    严格 vLLM 在 TP1/TP2、贪心/采样、有无 LoRA 的 8 种组合里，decode 时记下的 logprob 与事后 prefill 重算 0/512 不同；原生是 146–169/512。

  16. 训练侧 TP2 == TP1，连梯度都一样

    Megatron 严格 trainer：logprob 0/933 不同，LoRA 梯度 832 个张量的聚合哈希一致，一步 AdamW 后 LoRA 哈希一致。

  17. TP1 训练 OOM

    单次 8192 token 的打包在 80 GB 上放不下（权重就 56 GB）；默认 micro batch 改成 4096 token。

  18. 两边的 LoRA 哈希不是同一个定义

    Megatron 侧用 key+shape+bytes，E2E 用 name|dtype|shape；跨 env 桥的 agent 发现后统一到 muse_glimmer_lora_sha256_v1。

  19. Triton 把树折进了 MMA 链

    K 很小时每个 K 块只迭代一次，编译器把树的 7 个加法折成 3 个，约一半输出偏离契约；对抗 review 发现，强制两次迭代后修复。

  20. near-certain token 的 logp > 0

    两遍 softcap 内核的第二遍被编译成 FMA，最大值的 exp 不是 1；关掉 FP 融合后 0/2048。

  21. torch 2.13 的 Adam 在 CPU 上也会碰 GPU

    CPU 参数的 optimizer.step 会建 CUDA context，占住 GPU 0；mock 改用 CPU 安全的 Adam。

  22. 消融：原生漂移的来源

    拼 batch、KV cache、分块 prefill、注意力实现、logits 精度，任何一个都让 98–99% 的 token 变 bit；TF32、RoPE 表、换卡、换进程都是 0。

结论

RFC 需要怎么改

实现过程中才暴露的问题

F1 · Numerical requirements / O5 (attention backward)O5 反向规则不是 CP 不变的契约写的“dK/dV 按 query block 升序累加”在 CP 下做不到：每个 rank 只有自己的 query 块。CP 路径改用“整条序列 8 个规范 query 块、块间按 O3 树合并”，CP1/2/4 彼此相等，但和单卡一次性内核差在最后几位（相对 1.6e-5）。改契约：单卡内核也用同一个分块规则。
F2 · WS1 attention rows / WS2 TP注意力内核要接受头数参数两个严格注意力包装都把头数钉死在 32 个 Q / 2 个 KV，TP 分片后的 rank（TP2：16/1；TP4/8 复制 KV：8/1、4/1）不能直接调用，只能复制 KV 或 all-gather 头来绕。RFC 的注意力行要把 H_Q / H_KV 列为参数，并把“每个 rank 的头切片 == 全头计算的对应切片（逐 bit）”列为 TP 门。
F3 · weight_sync_identityBridge 把 final norm 存成 w−1Megatron Bridge 把 model.language_model.norm.weight 存成 bf16 的 (w−1)，bf16(w_meg+1) 有 1120/6656 个元素和 HF 不同。weight_sync_identity 要写明：这个张量从 HF checkpoint 重载，预期 626/627 个张量逐字节相同。
F4 · Projection grouping (to-freeze)Bridge 的 fused linear_qkv 布局每个 KV 组 g（4352 行）= [q 头 16g..16g+15（2048）| gate 头（2048）| k 头 g（128）| v 头 g（128）]；linear_fc1 = [gate; up]。已在真权重上 torch.equal 验证。严格路径要按这个布局拆开成四个独立 GEMM。
F5 · Validation table梯度容差要和尺度无关反向的比较用归一化误差（相对于参考梯度的范数），固定 atol 在 30B 的梯度尺度上没有意义。
F6 · Numerical requirements / O5O5 要写明 m = −inf 保护整行都被 mask 掉时（局部窗口的边界、padding）：α = 1，p = 0，不产生 NaN。
F7 · Open question 3 (LoRA)LoRA 不合并两边都用 y = bf16(acc32(W·x) + Σ B·z)；把 LoRA 合并进 W 会改变 bit。
F8 · WS1 table几行要改名或合并fused_add_rmsnorm → post_norm_residual_pre_norm（四范数夹心，(1+w) 增益，两个 eps 1e-5 / 1e-8）；注意力的 train / rollout 两行合成一行、两种执行模式；vocab_parallel_softcap_logp 并入 WS1 的 lm_head 行 + 一个传输行。
F9 · Foundation / environment版本钉在 transformers 5.17.0vLLM 0.31 要 transformers<5.18，Megatron Bridge main 要 ≥5.15,<5.18：语义源从 5.19 改钉 5.17（commit 856157a2）。5.17 和 5.19 的区别：RoPE 表的构造（5.17 是受 TF32 影响的 matmul）。
F10 · Hardware assumptions不要假设 Hopper仓库现有的严格内核（FA4 CuTe、SM90 线性 logp）在 A100 上不可用，原有 Triton 确定性 GEMM 只有 5 TFLOP/s。RFC 应把“一个与架构无关的 Triton 参考实现”列为基础行，Hopper 专用内核作为优化行。
F11 · final_e2e_lora / runtime layout两个运行时不能在一个进程里vLLM 0.31（torch cu130）和 Megatron Bridge + TransformerEngine（torch cu129）装不进同一个环境；E2E 需要跨进程的 trainer 桥，只传 token id、fp32 的 dL/dlogp 和带哈希的 LoRA。另外 Megatron 的 KV 头复制让 TP>2 暂时关闭，训练侧 TP 上限是 2。
