## Goal and scope
Support train–rollout consistency for meta-models/Muse-Glimmer-30B in RL-Kernel. Given the same tokens, weights, positions, masks and sampling context, strict training and rollout must produce exactly equal selected-token log-probabilities.
改Muse Glimmer is a 29.6B29.8B dense model, served by vLLM and SGLang and trainable through Megatron Bridge. It adds three things the repo does not cover today: gated, scale-normalized attention; alternating local (sliding-window, RoPE) and global (full causal, no positional encoding) layers on 2 KV heads; and a normalized embedding with a multiplied, soft-capped logit path. The BF16 checkpoint is 59.5859.55 GB, so everything except full-parameter end-to-end training fits one 8× H100 node.
- Phase A: the full 52-layer text model. Single-GPU kernels (WS1), multi-GPU execution (WS2), integration and a LoRA end-to-end run.
- Phase B: the vision input path.
改Speculative rollout with the bundledseparate DFlash drafter is left to a follow-up RFC; strict mode here runs with speculative decoding off. Quantized checkpoints, video input and the sampling RNG contract are out of scope.
No row is blocked on another RFC. Rows extend the Qwen3-8B dense track. Sibling rows in #415 and #434 are cited as "if landed", and the logit soft cap is shared through #542.

## Numerical requirements
The existing WS1 numerical standard applies:
改- Fixed accumulator precision and reduction order. No Split-K, Stream-K, split-KV or cross-block atomics unless the merge tree is fixed by contract. No TF32TF32, fast math, or fastFP math.contraction of recomputed values. Casts only at declaredthe points.points the contract declares. An attention row with no visible key yet produces no NaN.
- Batch invariance: a logical row's bytes do not change with batch size or batch position.
- Sequence-split invariance: a token's output is identical in training, prefill and decode, for any chunked-prefill split and any eviction timing around the 2,048 window.
改- One projection groupingOne projection grouping and Q-scale placement for(frozen Q/K/V/gateby the fingerprint) on both sides. A runtime that keeps its native fused projection is not in strict mode.
- Multi-GPU execution reproduces the single-GPU result byte for byte: the forward pass first (G1), then gradients (G2).
改- Fail closed (an error, never a fallback) on a Transformers-fallback model class, a config other than the pinned one, a missing strict kernel, a non-canonical projection grouping,grouping or Q-scale placement, RoPE on a global layer, an unsupported window or eviction mode, a native reducing collective, a zigzag CP layout, an undeclared KV ownership map, a weight-sync or RoPE-table hash mismatch, speculative decoding, vLLM's V1 model runner, prefix caching or speculativeKV decoding.offload.
改Parity uses torch.equal between two strict paths. Correctness uses allclose against an independent FP64 reference.reference of the frozen semantics; gradients use a normalized error. Exact per-operator rules are in docs/contracts/muse-glimmer-30b-strict-contract.md (lands with the first WS1 PR).
改Platforms. Each kernel PR carries the CUDA kernel and the Triton kernel, with the same arithmetic. The Triton kernel must also run on A100 (sm80); SM90-only kernels are optional fast paths. ROCm runs the Triton kernel; no ROCm-specific kernel code is added. PRs are validated on CUDA, including CUDA == Triton bitwise. ROCm is tested periodically on the Triton path once most rows have landed, and CUDA ↔ ROCm equality is measured then.

## Open questions
改1. Projection grouping. One fused Q/K/V/gate GEMM (as Megatron), fused Q/K/V plus a separate gate (as vLLM), or four GEMMs? Answered: four GEMMs (#558).
改2. K/V gradient rule. Is evaluation per canonical Q-head group the right rule, and can #415 and #434 share it? Answered here: yes, with replicas folded in rank order (kernel level at TP2/4/8 and CP2/4/8, end to end up to TP4). Sharing stays open.
改3. LoRA form. Unmerged W·x + B·(A·x) on both sides, or merged once on the trainer? Coordinate with #520. Answered: unmerged on both sides; merging changes bits.
4. Backward gate. Is G2 required for closeout, or is repeatability at a fixed topology enough for the first claim?
改5. Eviction policy. Evict eagerly at the window edge, or keep a fixed over-allocation so the speculative follow-up never has to restore evicted entries? Answered for strict mode: eager, keep the last 2,047 tokens; rollback is for the follow-up.
6. End-to-end scale. Is a LoRA run enough for closeout?
7. ROCm test rounds. Who runs them, and at which milestones?
8. Performance. A fixed ratio to native per operator, or report-only at first?
## Follow-up: speculative rollout
改The checkpoint ships a DFlash drafter ((separate repo meta-models/Muse-Glimmer-30B-assistant; 5 layers, 16-token blocks) that reads target hidden states at layers {1, 13, 25, 37, 49}. A follow-up RFC would add three contracts: one verify forward over k drafted tokens equals k single-token decodes; a rejected tail leaves every cachecache's visible window byte-equal to the non-speculative state; and the hidden-state tap changes no target byte.
